# Черновик: актуальный backlog PoC

> **Статус документа:** черновик на ревью, 2026-09-16. Ничего не закоммичено и
> не запушено. После согласования: содержимое заменяет раздел 0 в
> `docs/backlog.md`, выполненное уходит в `CHANGELOG.md`, а полный список идей
> (эпики 5–11) переезжает в `docs/roadmap.md`, чтобы не мешать.

**Стадия: Proof of Concept. Из неё мы не выходим.** Реального устройства пока
нет. Всё, что ниже, — проверка отдельных частей будущей системы (экран,
управление, меню, звуковой движок, отладка) в Wokwi и на ПК. Готовая часть не
означает, что PoC закончен.

**Критерий окончания PoC (без изменений):** MPK играет ноты → секвенсор на
4 дорожки по 16 шагов с ручным темпом и метрономом → сэмплер с чистым звуком,
который слышно на железе.

## A. Системный инструмент отладки и логирования

**Цель:** прошивка сама, без участия человека, записывает всё, что с ней
происходит, хранит это и отдаёт наружу. Читаем и разбираем логи **только на
компьютере**. На устройстве нет ни консоли, ни команд, ни отладочного экрана.

```
прошивка ──► Log ──► буфер в RAM ──┬─► Serial (поток, пассивно)   ──► ПК: файл
                                   ├─► файл на флеше/SD (сессии)   ──► ПК: выгрузка
                                   └─► (позже) Wi-Fi/HTTP отправка ──► ПК: приёмник
```

### A.1 Модуль логов `Log`
*Хочу единый логгер с уровнями и тегами.* **Готово, когда** весь вывод прошивки
идёт через него, а в коде не осталось голых `Serial.print`.
- [ ] `firmware/log.h/.cpp`: уровни `ERROR / WARN / INFO / DEBUG / TRACE`
- [ ] Теги подсистем: `SYS, INPUT, UI, MENU, SEQ, CLOCK, AUDIO, PERF`
- [ ] Одна строка = одна запись, формат для разбора программой: `123456 I INPUT NoteOn ch=10 n=52 v=100`
- [ ] Уровень задаётся **только при сборке** (`LOG_MIN_LEVEL`, по тегам через `#define`), в рантайме ничего не переключается
- [ ] В начале каждой сессии запись `SYS boot`: версия прошивки, хеш коммита, причина перезагрузки
- [ ] Перевести на логгер `firmware.ino`, удалить `dbg:`-принты (known issue №2), `heartbeat` перевести в TRACE

### A.2 Буфер в памяти
*Хочу, чтобы запись в лог никогда не тормозила цикл и звук.* **Готово, когда**
логгер пишет в кольцевой буфер, а наружу его сливает отдельная задача.
- [ ] Буфер фиксированного размера без `malloc` в рабочем цикле
- [ ] При переполнении теряются старые записи, в лог пишется счётчик потерь `SYS dropped=N`
- [ ] Можно вызывать из аудио-задачи (без блокировок)

### A.3 Хранение логов на устройстве
*Хочу, чтобы логи сохранялись, даже если компьютер не подключён.* **Готово,
когда** после перезагрузки логи прошлой сессии лежат в файле.
- [ ] Файлы по сессиям в LittleFS на флеше (сейчас), на SD (когда появится): `/logs/0007.log`
- [ ] Ротация: хранится последние N сессий или до лимита объёма, старые удаляются автоматически
- [ ] Запись на флеш пачками (раз в K секунд или при ERROR), чтобы не изнашивать флеш
- [ ] ERROR и причина падения сохраняются немедленно, чтобы пережить сбой

### A.4 Отправка логов наружу
*Хочу забирать логи на компьютер без действий на устройстве.* **Готово, когда**
каждый способ ниже доставляет лог в файл на ПК.
- [ ] **Serial-поток** (сейчас, Wokwi и USB): всё из буфера просто уходит в порт. В Wokwi поток пишется в файл через `wokwi-cli` (`--serial-log-file`)
- [ ] **Выгрузка сохранённых файлов** при подключении по USB: прошивка при старте сама отдаёт в Serial файлы сессий, которые ещё не выгружала, в обёртке `LOGFILE BEGIN/END` (без команд с ПК)
- [ ] **Отправка по Wi-Fi** (задел, не блокирует PoC): HTTP POST файлов сессий на адрес из конфигурации сборки

### A.5 Счётчики производительности в лог
*Хочу видеть, сколько стоят цикл и отрисовка.* **Готово, когда** раз в секунду
в лог пишется строка `PERF`, и по ней видно время цикла, кадра UI и число событий ввода.
- [ ] Макрос `PERF_SCOPE("ui.draw")` с min/avg/max за интервал
- [ ] WARN, если цикл дольше порога (например, 5 мс)
- [ ] Свободная heap/PSRAM в той же строке

### A.6 Инструменты на ПК (`tools/`)
*Хочу читать и разбирать логи на компьютере.* **Готово, когда** оба скрипта
работают с логом из Wokwi и с USB.
- [ ] `tools/log_capture.py`: слушает порт, пишет поток в файл, распаковывает выгруженные `LOGFILE`
- [ ] `tools/log_view.py`: фильтр по уровню, тегу и времени, сводка `PERF`
- [ ] Формат лога описан в `docs/logging.md`, он же является входом для E.2

## B. UX/UI-спецификация (документы, без кода)

**Цель:** зафиксировать логику до того, как писать экраны. Результат:
`docs/ux-spec.md`. Каждая подзадача — отдельный раздел, который можно
согласовать отдельно.

### B.1 Базовые принципы UX
**Готово, когда** раздел согласован, и дальше по нему проверяется каждый экран.
- [ ] Экран только показывает. Весь ввод идёт физическими элементами, тача нет
- [ ] **Выбранная дорожка:** крутилки и клавиши всегда относятся к ней
- [ ] **Один главный экран.** Меню открывается поверх и всегда возвращает на главный экран
- [ ] Не больше 2 уровней вложенности меню в PoC
- [ ] **Навигационный кластер вместо режимов-переключателей.** Одна и та же
  группа пэдов (см. B.4) двигает курсор и подтверждает выбор везде: в меню, в
  будущем браузере сэмплов, на главном экране. Джойстик из навигации выведен
  полностью — он остаётся только для игры (pitch/mod)
- [ ] Любое действие видно на экране в течение ~100 мс (подсветка и значение)
- [ ] Soft-catch-up крутилок (3.6): пока ручка не «догнала» значение, на экране видно цель и текущее положение
- [ ] Звук важнее экрана: отрисовка никогда не блокирует аудио (прицел на 9.5)

### B.2 Логика меню
**Готово, когда** описано дерево, навигация и поведение каждого пункта.

Предложение для обсуждения:

```
MENU (MODE, короткое нажатие)
├── TRACK      сэмпл дорожки · громкость · высота
├── TEMPO      BPM · метроном вкл/выкл · громкость метронома
├── INPUT      источник (Wokwi/MPK/Serial) · монитор событий
└── SYSTEM     ABOUT (версия, сборка, номер лог-сессии)
```

Навигация — единый навигационный кластер на 8 пэдов (раскладка физических
номеров зафиксирована в B.4), везде одинаковый:

| Действие | Пэд | Смысл |
|---|---|---|
| Курсор вверх | PAD6 | — |
| Курсор вниз | PAD2 | — |
| Назад / уровень выше / влево | PAD1 | выйти из пункта меню, подняться на директорию выше в браузере сэмплов; в горизонтальных списках/значениях — движение влево |
| Вперёд / провалиться внутрь / вправо | PAD3 | войти в пункт меню, спуститься в папку/выбрать сэмпл; в горизонтальных списках/значениях — движение вправо |
| Подтвердить (левый клик) | PAD5 | выбрать значение, применить |
| Отмена (правый клик) | PAD7 | отменить, выйти без сохранения |
| Контекстное действие A | PAD8 | значение зависит от экрана (см. B.4) |
| Контекстное действие B | PAD4 | значение зависит от экрана (см. B.4) |

PAD1/PAD3 — двойной смысл, не только вертикальная иерархия: это же пара
влево/вправо везде, где нужна горизонтальная навигация (шаг по списку
значений, перемещение по горизонтальной сетке и т.п.). Конкретный экран сам
решает, какой из двух смыслов (иерархия vs. горизонталь) сейчас активен.

- [ ] Решить: нужен ли автоповтор на PAD6/PAD2 при удержании (для длинных списков) и с каким интервалом
- [ ] Решить: поведение PLAY/STOP внутри меню (предложение: работает всегда, транспорт никогда не блокируется)
- [x] Отрисовка меню: **полноэкранные страницы** (не оверлей)

### B.4 Базовый layout управления

**Главное изменение (заменяет прежнюю схему с пэдами 1–4 = выбор дорожки).**
Пэды 1–8 (банк A) закреплены за одним и тем же навигационным кластером во
всех контекстах — принцип похож на геймпад: крестовина вверх/вниз/назад/
вперёд плюс «клик»-пара плюс два контекстных пэда. Раскладка снята с
физического макета (см. приложенную схему пэдов):

```
Верхний ряд:  PAD5  PAD6  PAD7  PAD8
Нижний ряд:   PAD1  PAD2  PAD3  PAD4
```
Номера — как на корпусе Akai. Ранее здесь стоял «дубль PAD3» в верхнем
правом углу — это была ошибка чтения мелкой подписи PAD8, дубля нет.
Прошивка видит только MIDI-ноты, роль вычисляется как
нота → номер пэда (`mpk_mapping.h`) → команда (`control_layout.h`).

| Пэд | Роль | Смысл |
|---|---|---|
| PAD6 | Вверх | курсор вверх — в меню, в браузере сэмплов, между дорожками на главном экране |
| PAD2 | Вниз | курсор вниз |
| PAD1 | Назад / влево | выйти на уровень выше — из пункта меню, из папки браузера сэмплов; в горизонтальном контексте — шаг влево |
| PAD3 | Вперёд / вправо | войти глубже — в пункт меню, в папку/файл на SD-карте; в горизонтальном контексте — шаг вправо |
| PAD5 | Подтвердить (аналог левого клика) | выбрать/применить значение |
| PAD7 | Отмена (аналог правого клика) | отменить/выйти без сохранения, контекстное меню (позже) |
| PAD8 | Контекст A | на главном экране: REC вкл/выкл (2.8); в меню: доп. действие пункта |
| PAD4 | Контекст B | на главном экране: метроном вкл/выкл (1.7); в меню: доп. действие пункта |

Так как банк A целиком занят навигацией, **выбор и запуск дорожки уходит на
клавиши**: нижние 4 клавиши (первая октава, C3–D#3) переключают выбранную
дорожку 1–4 и одновременно проигрывают её сэмпл на базовой высоте — это же
поведение, которое раньше давали пэды 1–4. Владелец не исключает, что часть
крутилок тоже будет дублировать выбор дорожки — решение отложено, крутилки
разбираются отдельной историей (3.6/B.3), для этой стори фиксируем только
поведение пэдов и клавиш. Банк B (пэды 9–16 на реальном MPK) остаётся
резервом под пошаговый ввод (2.12) и mute/solo (2.6) — в Wokwi банка B
физически нет (там только 8 пэдов), эти пункты открываются позже, на MPK.

| Элемент | Базовый слой | SHIFT (удержание MODE) |
|---|---|---|
| PLAY/STOP | старт с 1-го шага / стоп | — |
| MODE | короткое: меню; удержание: SHIFT | — |
| POWER (удержание) | вкл/выкл | — |
| Пэды 1, 2, 3, 6 | навигация (назад/вниз/вперёд/вверх, см. выше) | без изменений — кластер не переключается по SHIFT |

| Пэд 8 | REC вкл/выкл (2.8) | *резерв: overdub (2.9)* |
| Пэд 4 | метроном вкл/выкл (1.7) | *резерв: undo (2.10)* |
| Клавиши 1–4 (нижние) | выбрать дорожку 1–4 + сыграть сэмпл | *резерв: mute/solo (2.6)* |
| Остальные клавиши | хроматика сэмпла выбранной дорожки, пишутся при REC | *резерв: курсор по шагам* |
| K1–K4 | параметры выбранной дорожки | — |

## C. UI-каркас и первый основной экран (Wokwi)

### C.1 Менеджер экранов
*Хочу, чтобы экраны были отдельными объектами, а не методами одного класса.*
**Готово, когда** Boot, Home и Menu переключаются через один менеджер,
и каждый экран перерисовывает только изменённые зоны.
- [ ] Интерфейс `Screen { onEnter; onEvent(InputEvent); draw(dirtyMask) }`
- [ ] Кадровый бюджет: UI рисует не чаще N Гц и не дольше X мс за итерацию (замер через A.5)
- [ ] Текущий `UiScreens` разрезать на `BootScreen` и `HomeScreen`, логику питания убрать из `firmware.ino`

### C.2 Слой команд между вводом и логикой
*Хочу, чтобы сырые события превращались в команды.* **Готово, когда** логика
получает `SelectTrack(2)`, `TogglePlay`, `KnobDelta(k, d)`, а не номер CC.
- [ ] `InputRouter`: `InputEvent` + текущий слой (база/SHIFT/меню) → `Command`
- [ ] Навигационный кластер (PAD1/2/3/6/5/7/8/4, B.4) маппится на общие
