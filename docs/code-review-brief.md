# Бриф на код-ревью

Что владелец проекта ждёт от очередного код-ревью прошивки.

Это **не** просьба сразу реализовать функцию. Первая цель — понять текущий код, найти накопившиеся проблемы и выдать ревью, по которому можно действовать. Рефакторинг — отдельным шагом позже.

## Сначала прочитать

Перед ревью кода прочитайте:

1. `README.md`
2. `docs/architecture.md`
3. `docs/verification.md`
4. `docs/known-issues.md`
5. `docs/backlog.md`

`docs/archive/` — исторический материал, а не текущие требования.

## Цель ревью

Отревьюйте текущую прошивку как embedded/аудио-инженер, который впервые пришёл в проект.

Главный вопрос:

> Можно ли сопровождать и расширять текущий код, не опираясь на незадокументированные допущения и не накапливая случайную сложность?

Не оптимизируйте под сокращение числа строк. Оптимизируйте под:

- понятное владение;
- детерминированный тайминг;
- корректную конкурентность;
- предсказуемое потребление ресурсов;
- маленькие интерфейсы;
- возможность рассуждать о коде локально;
- поведение, подтверждённое доказательствами.

## Порядок ревью

### 1. Владение во время выполнения

Проследите цепочку:

```text
InputSource
    -> application layer
    -> Transport
    -> AudioEngine
    -> AudioSource / output
```

Найдите ответственность, которая сейчас принадлежит больше чем одному компоненту.

Особое внимание — `firmware.ino`, `Transport`, `AudioEngine` и `PatternExporter`.

### 2. Конкурентность

Проверьте каждое значение, которое пересекает границу задачи или ядра.

Ищите:

- гонки данных;
- устаревшие снимки состояния;
- неверные границы критических секций;
- небезопасный порядок публикации;
- очереди, которые могут молча терять события;
- состояние интерфейса, которое читает сторона звука;
- состояние звука, которое меняет код интерфейса.

Не добавляйте блокировки механически. Объясняйте, зачем нужен каждый примитив синхронизации.

### 3. Звуковой тракт

Проверьте:

- границы блоков рендера;
- семантику отложенных запусков;
- время жизни голосов;
- интерполяцию;
- клиппинг;
- усиление микшера;
- измерение пиков;
- владение кольцевым буфером звука;
- работу в прерывании.

Существующая побитовая регрессия — инвариант, если только осознанное продуктовое решение не меняет семантику звука.

### 4. Транспорт

Убедитесь, что:

- музыкальное время не зависит от отрисовки интерфейса;
- у смены BPM понятная семантика границы;
- запуск и остановка детерминированы;
- тайминг шагов не накапливает дрейф от целочисленного деления;
- видимое интерфейсу состояние плейхеда не может испортить музыкальные часы.

### 5. Ввод

Проверьте:

- семантику событий;
- подавление дребезга;
- агрегацию приращений энкодеров;
- ёмкость очереди;
- порядок событий;
- обработку NoteOn/NoteOff;
- отделение ввода, специфичного для Wokwi, от общей логики ввода.

### 6. Память и конфигурация сборки

Изучите:

- статическую RAM, включая два экземпляра `AudioEngine` с таблицами щелчка под 48 кГц ([known-issues, п. 6](known-issues.md#6-два-экземпляра-audioengine-занимают-треть-статического-dram));
- размеры стеков;
- дублированное состояние;
- сэмплы во флеше;
- использование PSRAM;
- конфигурацию платы;
- допущения о разметке разделов;
- запас кольцевого буфера против будущих операций с флешем ([known-issues, п. 10](known-issues.md#10-запись-во-флеш-даст-паузу-в-звуке)).

Отделяйте измеренные значения от оценок.

### 7. Интерфейс и слой приложения

Проверьте `firmware.ino` на случайные связи и устаревшее состояние.

Не разбивайте его на фреймворк по умолчанию. Сначала найдите конкретные обязанности, которые порождают баги или мешают рассуждать об изменении.

### 8. Ошибки и граничные случаи

Посмотрите на:

- пустые паттерны;
- многократные запуск/остановку;
- отмену экспорта;
- одновременный ввод;
- переполнение очередей;
- максимальный и минимальный BPM;
- границы параметров;
- границы окончания сэмпла;
- отказы выделения памяти;
- запуск и выключение устройства.

## Проверка качества кода, написанного с ИИ

Отдельно ищите паттерны, которые часто появляются, когда LLM наращивала кодовую базу без последующей ручной чистки:

- абстракции, использованные один раз;
- интерфейсы без реальной альтернативной реализации;
- дублированное состояние, описывающее одно и то же;
- защитный код без продемонстрированного сценария отказа;
- длинные комментарии, пересказывающие историю разработки вместо текущего инварианта;
- спекулятивную поддержку будущего железа;
- повторяющиеся преобразования между представлениями;
- код, который выглядит обобщённым, а на деле зашит под частный случай;
- тесты, описывающие реализацию, а не поведение;
- вводящие в заблуждение имена или комментарии, оставшиеся после рефакторинга.

Это цели ревью, а не выводы. Прежде чем советовать удаление, укажите конкретный код.

## Согласованность документации и кода

Для каждого существенного расхождения укажите:

```text
Документация говорит:
Код делает:
Доказательство:
Риск:
```

Не переосмысляйте документацию молча.

## Результат

Сначала выдайте ревью с разделами:

```text
Архитектура
Конкурентность
Звук
Транспорт
Ввод
Память / сборка
Интерфейс / слой приложения
Тесты
Расхождения с документацией
Лишняя сложность
Приоритетные рекомендации
```

Для каждой находки укажите:

- серьёзность;
- точный файл и функцию;
- почему это важно;
- доказательство;
- предлагаемое направление.

Не заявляйте о проверке на железе там, где её не было.

Не переписывайте код ради демонстрации активности.

Какие находки станут работой по рефакторингу, решает владелец проекта.
