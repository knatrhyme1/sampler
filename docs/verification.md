# Проверка

В проекте несколько сред проверки, потому что ни одна не доказывает систему целиком.

## Тесты на ПК

### Регрессия звука

```bash
python tools/audio_bitexact_test.py
```

Зачем:

- сравнить исторический посэмпловый эталонный рендер с текущим блочным;
- ловить ошибки интерполяции и границы окончания голоса;
- покрыть несколько частот дискретизации и размеров блока;
- защитить побитовую неизменность звука.

Этот тест не доказывает, что финальный вывод на железе звучит правильно.

### Регрессия транспорта

```bash
python tools/transport_timing_test.py
```

Зачем:

- сверить границы шагов с арифметикой во времени сэмплов;
- покрыть несколько значений BPM;
- покрыть разные размеры блока;
- защитить накопление остатка и фазу транспорта.

Этот тест не доказывает физическую задержку.

### Самотест прошивки на ESP32-S3

```bash
python tools/firmware_selftest.py --compile
```

Два теста выше проверяют модель алгоритма на Python, а не код прошивки: сломанный `audio_engine.cpp` они не заметят. Самотест закрывает этот разрыв. Скрипт собирает скетч из исходников прошивки как есть (`AudioEngine`, `Transport`, встроенные сэмплы) и вшивает в него эталонные CRC, посчитанные Python-моделью.

Как прогнать:

1. `python tools/firmware_selftest.py --compile` — скетч появится в `build/firmware_selftest/firmware_selftest.ino`, `--compile` проверит, что он собирается.
2. Открыть <https://wokwi.com/projects/new/esp32-s3> (новый проект, сохранять не нужно), заменить `sketch.ino` содержимым скетча, запустить.
3. Дождаться последней строки в Serial Monitor: `SELFTEST: PASS` или `SELFTEST: FAIL`. На видимой вкладке прогон занимает несколько минут; на свёрнутой симуляция замедляется в разы.

Что проверяется:

- `engine` — звук движка бит в бит против Python-эталона, блоки режутся на границах шагов, как в экспорте;
- `transport` — живой путь через `Transport::render` с теми же сценариями, в том числе блоками по 256 сэмплов, как будет просить I2S-вывод;
- `timing` — каждый шаг звучит ровно на своём сэмпле при разных BPM и размерах блоков.

Прогоняйте после любой правки в `audio_engine.*`, `transport.*` или `step_sequencer.h`.

Самотест проверяет себя сам: если внести ошибку в интерполяцию или в учёт остатка в часах, он падает (проверено мутацией 19.09.2026).

## Сборка прошивки

```bash
arduino-cli compile -e firmware
```

Целевая конфигурация сборки под ESP32-S3 N16R8 закреплена в `firmware/sketch.yaml`.

Успешная сборка доказывает компиляцию под эту конфигурацию. Она не доказывает, что образ прошит в настоящее железо.

## Wokwi

Симуляция в Wokwi сейчас покрывает:

- питание и загрузочный экран;
- опрос ввода;
- навигацию пэдами;
- энкодеры;
- редактирование шагов;
- транспорт;
- метроном;
- интерфейс микшера;
- интерфейс piano roll;
- превью аранжировки;
- симулированный однобитный вывод;
- сценарий экспорта в WAV.

Wokwi не доказывает:

- USB-MIDI на настоящем MPK, включая питание MPK от батареи через повышающий модуль;
- поведение кодека WM8960;
- работу от аккумулятора;
- физическую задержку звука;
- реальный тайминг хранилища, включая паузу звука при записи во флеш ([known-issues, п. 10](known-issues.md#10-запись-во-флеш-даст-паузу-в-звуке));
- реальное поведение памяти в финальной аппаратной сборке.

## Проверка всего функционала

Разовая сплошная проверка устройства — не регрессия, а сессии по сценариям: машина состояний экранов, границы параметров, прерывания, флуд ввода, экспорт.

- [`test-plan-2026-09-20.md`](test-plan-2026-09-20.md) — сценарии, оракулы («норма — где смотреть») и порядок прогона.
- [`test-report-2026-09-20.md`](test-report-2026-09-20.md) — что дал последний прогон и какие находки из него вышли.

План стоит на общепринятых приёмах, а не на выдуманном процессе: покрытие переходов состояний, «атаки» Уиттекера, шпаргалка эвристик, RCRCRC для выбора регрессии, soap opera testing и monkey testing. Источники перечислены в самом плане.

Повторять целиком нужно не после каждой правки, а перед заметной вехой. После точечной правки берите из плана только затронутые группы.

## Путь экспорта до файла на диске

```bash
# страница с закладкой; на Windows — tools/export_bookmarklet.bat
tools/export_bookmarklet.html
```

Что доказано 20.09.2026: закладка (ровно тот код, что попадает в браузер) собрала файл из Serial Monitor и скачала его. CRC32 файла на диске совпала с той, что напечатала прошивка; заголовок WAV — 44,1 кГц, моно, 16 бит.

Чего это не доказывает: что звук в файле музыкально осмыслен ([known-issues, п. 12](known-issues.md#12-смысл-экспорта-ещё-нужно-окончательно-проверить-на-слух)).

Запасной путь, когда файл не скачался, а текст в мониторе остался, — `tools/wav_from_serial.py`: он собирает WAV из сохранённого текста и сверяет ту же CRC32.

## Язык доказательств

Используйте термины точно:

- **Проверено** — воспроизведено конкретным тестом или замером.
- **Наблюдалось** — видели в какой-то среде, но не обязательно покрыто повторяемым тестом.
- **В симуляции** — показано только в Wokwi.
- **Не проверено на железе** — нужно настоящее железо.
- **Гипотеза** — правдоподобное объяснение, ещё не подтверждённое замером.

Сборка, прогон симуляции и прослушивание — это разные виды доказательств.
