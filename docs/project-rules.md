# Правила проекта

Устойчивые правила, по которым ведётся SMPLR. Они не про конкретную задачу
и меняются только сознательно.

Главный принцип:

> **Сначала факт о продукте, потом документация о нём.**

## Продукт

- Публичный репозиторий и локальная работа — разные состояния. Не выдавать
  незакоммиченное за опубликованное.
- Дорожная карта — не реализация. Планы и факты не смешивать в одном
  предложении.
- Проверка в симуляции не равна проверке на железе.
- Неизвестное называть неизвестным. Не выдумывать распиновку, ток,
  характеристики модуля или результат замера.
- Компонент считается выбранным только после подтверждения документацией
  конкретной модели. Стадии закупки ведутся явно:
  `Candidate → Selected → Ordered → Arrived → Bench-tested → Integrated`.
- Запуск на железе — обязательный этап до расширения всего, что зависит от
  железа.

## Внешний контроллер и локальные контролы

- Akai MPK mini mk3 — **одно внешнее USB-MIDI устройство**.
- Его клавиатура, пэды, крутилки и джойстик не являются отдельными входами
  SMPLR. В архитектуре, схеме, карте выводов и списке компонентов они не
  фигурируют как отдельные блоки.
- Джойстик MPK — орган управления контроллера, а не подсистема SMPLR.
- PAD1–PAD8 сейчас несут навигацию и транспорт. Это UX-эксперимент, а не
  решение по корпусу.
- `POWER`, `PLAY/STOP`, `MODE` — будущие кнопки самого SMPLR. Их набор и
  расположение не утверждены.
- Кнопки с RGB-подсветкой — идея на будущее. В список компонентов и карту
  выводов не попадают.
- Логические команды (PLAY, STOP, вверх, вниз) и их физический источник
  описываются отдельно: источник может измениться, логика — нет.

## Документация

- Документация пишется для человека, а не для модели.
- Короче — лучше. Таблица вместо трёх абзацев, ссылка вместо копии текста.
- На каждую тему — один источник правды.
- Мета-шума нет: ни истории обсуждений, ни заметок для следующего агента,
  ни рассуждений по ходу работы.
- Отчёты отдельных прогонов, сырые логи и журналы работы в репозиторий не
  попадают. Публикуется устойчивый вывод: «регрессии зелёные», «задержка
  8,4 мс», «на железе не проверено».
- Измеренная величина публикуется как факт с пометкой `Provisional`, если
  замер предварительный.
- Комментарий в коде объясняет инвариант, ограничение железа или владение —
  а не историю правок.

## Инженерия

- Прошёл тест в симуляции — это результат симуляции, не железа.
- Аппаратные предположения должны быть проверяемыми.
- Архитектурные решения фиксируются в [`decision-log.md`](decision-log.md).
- Интерфейс не ломает тайминг звука ни при каких обстоятельствах.
- Особенности среды разработки остаются в адаптерах и конфигурации.
- Найденная архитектурная проблема попадает в
  [`known-issues.md`](known-issues.md) или [`backlog.md`](backlog.md), а не
  чинится большим рефакторингом по ходу другой задачи.

## Работа с ИИ

В проекте используется Claude Code. Это не меняет требований к результату:

- рабочие материалы — логи, черновики, отчёты прогонов — остаются
  локально;
- в репозиторий уходит только знание о продукте;
- сгенерированный код проходит ревью, тесты и замеры наравне с любым
  другим;
- временная UX-гипотеза не превращается в архитектурное решение без
  подтверждения владельца.
