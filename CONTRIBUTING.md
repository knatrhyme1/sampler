# Как участвовать

SMPLR — экспериментальный embedded/аудио-проект. Кода немного, поэтому понимать текущую архитектуру важнее, чем следовать громоздкому процессу.

## С чего начать

Читайте по порядку:

1. [`README.md`](README.md) — текущее состояние и как запустить.
2. [`docs/architecture.md`](docs/architecture.md) — кто чем владеет и как идёт выполнение.
3. [`docs/known-issues.md`](docs/known-issues.md) — ограничения и доказательства.
4. [`docs/verification.md`](docs/verification.md) — что может доказать каждая среда.
5. [`docs/backlog.md`](docs/backlog.md) — активная работа.
6. [`docs/roadmap.md`](docs/roadmap.md) — дальние планы.

Файлы в `docs/archive/` — исторические документы, а не текущие требования.

## Сборка и тесты

Прошивка:

```bash
arduino-cli compile -e firmware
```

Регрессия звука:

```bash
python tools/audio_bitexact_test.py
```

Регрессия транспорта:

```bash
python tools/transport_timing_test.py
```

Самотест прошивки (настоящий C++ движка и транспорта, прогоняется в Wokwi):

```bash
python tools/firmware_selftest.py --compile
```

Дымовой тест на ПК:

```bash
cd sound-engine
make test
```

Проверка в Wokwi описана в `docs/verification.md`. Там же — план сплошной проверки функционала и отчёт последнего прогона.

Изменение не считается проверенным на железе, пока его не прогнали на настоящей целевой плате.

## Прежде чем менять код

Сначала выясните:

- какой модуль владеет поведением;
- в каком контексте или задаче оно выполняется;
- какие у него требования по времени;
- какой тест или замер его защищает.

Не чините проблему новой абстракцией, если существующая граница ответственности на самом деле справляется.

## Pull request'ы и коммиты

Хорошее описание изменения отвечает на четыре вопроса:

```text
Что изменилось
Зачем
Что проверено
Что проверить не удалось
```

Сообщения коммитов — короткие. Подробные доказательства место в тестах, задачах или технической документации, а не в длинном сгенерированном рассказе в коммите.

Заметное пользователю изменение добавляет строку в [`CHANGELOG.md`](CHANGELOG.md) под `[Unreleased]`. Решённая проблема переносится из `docs/known-issues.md` в раздел `Fixed` журнала и удаляется из списка проблем. Старые записи журнала не переписываются.

## Правила документации

Текущая документация описывает текущий репозиторий.

Разделяйте состояния явно:

- **Реализовано** — есть в текущем коде и подтверждено.
- **Превью** — есть интерфейс или модель данных, но сама функция не доделана.
- **Открытая проблема** — ограничение или баг, влияющий на поведение сейчас.
- **Будущее** — запланировано, но не реализовано.
- **Не проверено на железе** — нельзя доказать ни в Wokwi, ни на ПК.

Не смешивайте эти состояния в одном предложении.

Не ведите дневник разработки в комментариях к коду. Комментарий объясняет неочевидный инвариант, аппаратное ограничение, владение или причину, которая всё ещё актуальна для кода.

Историческим решениям место в журнале изменений или в архиве.

## Разработка с ИИ

В проекте используется Claude Code.

Это не исключение из дисциплины ревью. Сгенерированный код должен быть:

- сверен с текущей архитектурой;
- протестирован;
- измерен там, где важны время и производительность;
- упрощён, если реализация сложнее задачи.

Сгенерированный текст, сгенерированные тесты и успешная компиляция сами по себе доказательством не считаются.
